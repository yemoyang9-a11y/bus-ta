# 도착정보 갱신과 비콘 스캔 시작 시점

버스 도착 예정 시간을 언제 다시 조회할지, 스마트지팡이 비콘 스캔을 언제 켤지 정하는 정책이다.

- 코드: `apps/server/src/services/arrival/arrival-poll-policy.ts`, `arrival-cache.ts`
- 상태: **정책과 캐시만 구현됨. 아직 어떤 API에도 연결되어 있지 않다.** 연결에는 아래 "남은 작업"의 협의가 필요하다.

## 왜 필요한가

현재 `getArrivalInfo`는 `POST /api/trips`에서 한 번만 호출된다. `PATCH /api/trips/{tripId}/status`에는
GBIS 호출이 없어서, 사용자가 정류장에서 기다리는 동안 "약 3분 후 도착"이 갱신되지 않는다.

그렇다고 앱의 3초 주기에 맞춰 GBIS를 부를 수는 없다. 그래서 호출 시점을 앱이 아니라 서버가 정한다.

## 근거가 된 실측

2026-08-24, GBIS를 20초 간격으로 12회 조회. 스크립트는 저장소 루트 `gbis-volatility.mjs`.

| 측정 | 심야 00:24 | 퇴근 18:42 사당 | 퇴근 18:42 수원대 |
|---|---|---|---|
| 추적된 노선 | 2~4개 | 24개 | 15개 |
| 20초당 최대 감소(이상치 제외) | 1~2분 | 1~2분 | 1~2분 |
| 4분간 감소 속도 | 실시간의 1~1.3배 | 최대 1.5배 | 최대 1.5배 |
| 분 단위 되돌아감 | 일부 | 24개 중 10개 | 15개 중 4개 |
| 정거장 수 되돌아감 | 0개 | 24개 중 6개 | 15개 중 2개 |

세 가지를 확인했다.

1. **예측값은 러시아워에도 급락하지 않는다.** 정체가 심해도 감소 속도는 실시간의 1.5배 안쪽이다.
2. **값이 되돌아가는 일은 흔하다.** 예측이 틀린 것이 아니라 앞차가 도착·출발해서 다음 차량 기준으로
   바뀐 것이다(720-2번: 1분 → 9분). 심야에는 배차가 뜸해 4분 안에 관측되지 않았을 뿐이다.
3. **단발성 이상치가 실재한다.** 1008번이 37분 → 1분 → 37분으로 한 번 튀었다가 원복했다.
   단일 샘플로 판단하면 안 된다.

## 갱신 주기

```
다음 조회까지 = clamp(남은시간 ÷ 2, 20초, 5분)
```

남은시간의 절반을 기다리면, 예측값이 최악(1.5배)으로 줄어도 다음 조회 시점에 25%가 남아
도착을 건너뛰지 않는다. 30분 남은 상태에서 도착까지 약 9회 호출한다(1분 주기면 30회).

도착정보가 없으면(심야·미운행·GBIS 미수록 노선) 조회를 멈추지 않고 최대 주기로 재시도한다.
값이 없다고 멈추면 나중에 운행이 시작돼도 알아채지 못한다.

## 비콘 스캔 시작 시점

```
남은시간 ≤ 5분  →  스캔 시작. 한 번 켜면 탑승 확정까지 끄지 않는다.
```

두 가지가 중요하다.

- **끄지 않는다.** 위 실측 2번 때문이다. 앞차가 떠나 값이 커졌을 때 스캔을 끄면,
  정작 버스가 눈앞에 온 순간에 꺼져 있게 된다.
- **도착정보가 없으면 켠다.** GBIS에 없는 노선이거나 실시간 값이 빈 경우 스캔을 막으면
  비콘 감지가 영영 시작되지 않아 자동 탑승 판정이 동작하지 않는다.
  배터리보다 탑승을 놓치지 않는 쪽을 우선한다.

## 캐시 동작

`ArrivalCache`가 "정류장 + 노선" 단위로 도착정보를 들고 있으면서, 갱신 시점이 지났을 때만
실제로 GBIS를 부른다. 호출부는 평소처럼 물어보기만 하면 된다.

**실패와 "차량 없음"을 구분한다.**

| 반환 | 뜻 |
|---|---|
| `arrivals: [...]` | 정상 조회, 도착 차량 있음 |
| `arrivals: []` | 정상 조회, 실시간 차량 없음 |
| `arrivals: null` | 조회 실패 |

GBIS는 요청이 잘못돼도 HTTP 200으로 응답하고 `msgHeader.resultCode`에만 이유를 담는다
(실측: 없는 정류장 `resultCode 4`, 파라미터 누락 `resultCode 2`). 어댑터가 `resultCode === 0`
일 때만 목록을 읽으므로, 호출 실패가 "실시간 차량 없음"으로 둔갑하지 않는다.

**낡은 값에는 시한이 있다.** 갱신에 실패하면 직전 값을 `maxStaleMs`(기본 90초) 동안만 더 쓴다.
일시적인 오류에 안내를 비우면 버스가 사라진 것처럼 보이지만, 무기한 유지하면 GBIS가 죽은 동안
이미 지나간 버스를 계속 "N분 후 도착"이라고 안내하게 된다. 시각장애인 안내에서는 낡은 값이
값 없음보다 위험하다. 실패 뒤에는 최소 간격(20초)으로 빠르게 재시도해 정상 값을 되찾는다.

**동시 요청은 하나로 합친다.** 같은 대상에 요청이 겹치면 진행 중인 조회를 공유해 GBIS를 한 번만 부른다.

**사용자별 상태는 담지 않는다.** 이 캐시는 프로세스 전역이라, 비콘 스캔 여부처럼 운행마다 달라지는
값을 넣으면 같은 정류장을 쓰는 다른 사용자에게 새어 나간다. 스캔 판단은 호출부가 자기 운행 상태와
함께 `shouldScanBeacon`을 직접 호출한다.

## 남은 작업 (협의 필요)

이 정책을 실제로 태우려면 다른 파트와 맞춰야 한다.

- **`PATCH /status` 응답에 도착정보·스캔 신호를 실을지** — 응답 구조가 바뀌므로
  `docs/API_SPEC.md`, `docs/MODULE_CONTRACTS.md` 동기화와 예모·채린 확인이 필요하다.
- **앱이 스캔 신호를 받아 `START_BEACON_SCAN`을 보내는 부분** — 프론트엔드·BLE 담당 범위다.
  현재 스캔 시작 코드는 `RouteListScreen`(화면 터치 경로)에만 있고 `realtime/`(음성 경로)에는 없다.
- **스캔 시작 시점 5분이 적절한지** — 실측이 4분 창이라 더 긴 구간의 데이터는 없다.
  지팡이가 비콘을 잡는 데 걸리는 실제 시간을 하드웨어 담당과 맞춰 조정할 수 있다.
