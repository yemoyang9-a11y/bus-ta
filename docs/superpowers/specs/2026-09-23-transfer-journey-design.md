# 환승 여정 이어가기 설계

## 목표

환승 후보를 선택하면 앱이 도보·버스·지하철 구간을 순서대로 안내한다. 한 버스 구간의 목적 정류장에 도착해도 전체 여정은 끝내지 않는다. 사용자가 실제 하차를 음성이나 버튼으로 확인한 뒤 다음 구간을 안내한다. 마지막 구간의 완료 확인 후에만 전체 여정을 종료한다.

## 구조

기존 서버 trip은 버스 한 구간만 표현한다. 환승 후보 전체를 단일 버스 운행으로 합치지 않는다. 앱이 전체 여정과 현재 구간을 유지하고 각 버스 구간에서 기존 POST /api/trips를 사용한다. 직행 버스의 현재 운행·하차벨·종료 동작은 보존한다.

환승 후보의 각 버스 segment에 busLeg(routeNo, localBusId, gbisStationId, boardingStation, destinationStation, stationList)를 추가한다. 하나라도 불완전하면 실행 가능한 여정으로 표시하지 않는다. tripSupported=false는 단일 서버 trip 생성 불가를 뜻하고 journeySupported=true는 앱이 구간별로 진행할 수 있음을 뜻한다. 공개 필드는 camelCase이며 ODsay 숫자형 내부 값은 노출하지 않는다.

## 상태와 확인

앱은 선택 후보와 segmentIndex를 보관한다. 도보는 도착 확인, 지하철은 탑승과 하차 확인, 버스는 서버 TRIP_DONE 이후 실제 하차 확인을 요구한다. 버스 TRIP_DONE은 해당 구간만 종료한 것이므로 전체 여정 완료 문구나 상태 초기화를 하지 않는다. 하차 확인 뒤 다음 구간으로 이동한다. 다음 버스 정류장에 도착하면 사용자가 시작을 요청하고 그 구간 busLeg로 새 서버 trip을 만든다. 서버 성공 전 새 탑승 대기·BLE·하차벨 성공을 표시하지 않는다.

화면 버튼과 음성 Function은 같은 단계 전이 규칙을 사용한다. 모델은 서버가 확인하지 않은 버스 탑승, 사용자가 확인하지 않은 하차, GPS만으로 알 수 없는 지하철 하차를 단정하지 않는다. 늦은 이전 trip의 위치·BLE·음성 결과를 새 구간에 반영하지 않는다.

## 제한

지하철은 ODsay 정적 노선·역 이름만 안내하며 실시간 열차 위치·하차벨·지하 GPS 추적은 없다. 도보는 구간 시작·종점 안내와 사용자 확인을 제공하며 턴바이턴 내비게이션은 아니다. 앱 프로세스가 종료되면 메모리 여정 커서는 복원되지 않는다. 버스 구간 생성 실패는 현재 단계에서 재시도한다. 운영 DB 스키마·외부 키·배포 설정은 변경하지 않는다.

## 검증

- 버스→도보→버스, 도보→지하철→도보→버스, 버스→지하철, 버스 3개 구간을 순서대로 진행한다.
- 중간 TRIP_DONE에서 전체 완료 안내가 없고 실제 하차 확인 뒤에만 다음 구간으로 이동한다.
- 중복 확인, 이전 trip 늦은 응답, 취소·재시도, 마지막 구간 종료를 검사한다.
- 직행 버스·하차벨 회귀, 타입 검사, 서버 테스트, Android 번들을 확인한다.
- 실제 ODsay·GBIS 표본과 휴대폰·버스·지팡이 현장 검증은 별도다.
