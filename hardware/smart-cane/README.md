# 스마트 지팡이 (White_cane)

시각장애인이 버스를 찾을 수 있도록 BLE 비콘을 스캔해 거리·상태를 진동으로 안내하는 ESP32 코드입니다.

## 코드
- `ble_stick.ino`
- `proximity-feedback.h`: Arduino에 의존하지 않는 PWM 제어기와 스캔/명령 mailbox
- `tests/proximity-feedback.test.cpp`: 시간·RSSI·명령 순서를 재생하는 호스트 시험
- 기존 `ble_stick/ble_stick.ino` 하위 사본은 이 변경의 대상이 아닙니다. 빌드할 때 위 두 원본 파일을 같은 `ble_stick` 스케치 폴더에 복사합니다.

## 역할
- **BLE 스캔**: 버스 비콘(`BUS_1551_001`)을 스캔해서 RSSI로 거리·상태 판정
- **진동 안내**: 새로 관측한 RSSI에 따라 GPIO25 PWM을 점진적으로 조절
- **앱 명령 수신**: 앱에서 스캔 시작/중지, 타겟 비콘 지정
- **상태 전송**: 판정한 상태를 앱에 Notify로 전송 (진동 + 음성 안내 연동용)

## 핀 설정
- GPIO25: 진동모터
  - 개발/테스트: 진동모터 모듈
  - 최종: 원통형 진동모터(DVM6C-J) + 2N2222 트랜지스터 회로
- PWM은 `analogWrite(25, 0..255)`를 사용합니다. 모터를 GPIO에 직접 연결하지 않고 모터 구동 회로를 거칩니다. 최종 회로의 전원·공통 접지·플라이백 다이오드 및 실제 모터의 최소 구동 duty를 실물로 확인해야 합니다.

## BLE
- device name: `White_cane`
- Service UUID: `4fa45540-8201-11e5-8223-0002a5d5c51b`
- Characteristic UUID: `4fa45541-8201-11e5-8223-0002a5d5c51b`
- 명령 수신(Write, JSON):
  - `{"cmd":"SET_TARGET_BEACON","target":"BUS_1551_001"}`
  - `{"cmd":"START_BEACON_SCAN"}`
  - `{"cmd":"STOP_BEACON_SCAN"}`
- 앱은 연결 및 서비스 탐색 후 `SET_TARGET_BEACON`의 Write 응답을 기다리고,
  성공한 경우에만 `START_BEACON_SCAN`을 이어서 보낸다.
- 상태 전송(Notify, JSON):
  - `{"state":"APPROACHING","rssi":-65}`
  - state 종류: APPROACHING / ARRIVED / PASSING / PASSED_STOPPED / LEAVING
- 유효한 상태를 처음 판정한 뒤에는 상태가 같아도 타깃이 관측된 스캔마다 약 1초 간격으로 원시 RSSI를 보냅니다. 상태 변경은 다음 주기를 기다리지 않고 전송합니다. 모터 출력을 위한 필터 값이나 과거 RSSI를 새 표본처럼 전송하지 않습니다.
- 기존 상태 계약을 유지하므로 초기 `NONE`은 전송하지 않습니다. 최초 상태 판정에는 최소 6개 표본이 필요하며 안정된 근접 신호는 보통 8개 표본 이후 `ARRIVED`가 됩니다. 신호가 약하고 추세도 없으면 이보다 오래 걸릴 수 있습니다. 앱 자동 탑승 감지는 첫 유효 Notify 이후의 새 표본으로 판단해야 합니다.
- 연결 해제 시 재광고하므로 재부팅 없이 다시 연결할 수 있습니다. 연결 해제 자체는 STOP으로 취급하지 않습니다.
- 명령 수신용 특성 값과 Notify 송신 버퍼를 분리합니다. SDK 이벤트 태스크가 regular Write와 prepared/EXEC_WRITE를 완료한 뒤 수신 값을 복사하며, Notify는 그 특성 값을 덮어쓰지 않고 별도 JSON 버퍼로 전송합니다.
- Notify는 해당 연결이 CCCD 알림 구독을 켰고 JSON 전체가 협상된 `MTU - 3` 안에 들어갈 때만 보냅니다. 부족한 MTU에서는 JSON을 자르거나 나누지 않습니다. 앱은 MTU 64 이상을 확보해야 합니다(기본 MTU 23만으로는 부족). JSON 버퍼는 64바이트이며 실제 전송은 61바이트 이하로 제한합니다.
- 펌웨어도 광고를 시작하기 전에 로컬 MTU 상한을 185로 설정합니다. 설정 실패 시 모터 0을 유지하고 광고를 시작하지 않습니다. 앱과 실제로 협상된 값은 연결별 MTU 이벤트로 다시 확인합니다.
- 연결 해제와 connId 재사용 시 이전 구독과 MTU를 초기화합니다. 앱은 새 연결마다 다시 구독해야 합니다. 연결별 메타데이터 갱신과 송신은 명령/출력과 같은 태스크 뮤텍스를 사용합니다.

## 상태 판정
RSSI 평균+추세 기반으로 버스 상태를 판정합니다:
- **APPROACHING**: 접근 중
- **ARRIVED**: 다가와서 앞에 정차 (탈 수 있음)
- **PASSING**: 지나가는 중
- **PASSED_STOPPED**: 지나가서 다른 곳 정차 (이동 필요)
- **LEAVING**: 멀어짐

상태 판정과 진동 제어는 분리되어 있습니다. 이전 `PASSING`/`LEAVING` 상태가 남아 있어도 신호가 다시 가까워지면 진동이 회복됩니다.

## 점진적 진동과 명령 처리

- RSSI `-90..-55 dBm`을 PWM `0..255`에 대응시킵니다. 최대 상승 속도는 전체 범위 기준 600ms, 하강 속도는 1200ms이며 `loop()`의 약 20ms 주기로 진행합니다. 실제 거리나 체감 세기에 대한 보정 완료 값은 아닙니다.
- 마지막 새 신호에서 1200ms까지 출력 목표를 유지하고, 이후에는 0으로 점진적으로 감쇠합니다. 한 스캔 누락으로 즉시 꺼지지 않으며 장기 누락 뒤 약한 신호가 돌아와도 다시 진동합니다.
- `STOP_BEACON_SCAN`은 다음 제어 주기(통상 약 20ms)에 감쇠 없이 PWM 0으로 전환합니다. `START_BEACON_SCAN`과 타깃 변경은 이전 출력·추세·Notify 주기를 초기화합니다.
- BLE 명령 수락과 `loop()`의 표본 소비·Notify·PWM 적용은 같은 일반 태스크 뮤텍스로 직렬화합니다. 출력 도중 명령이 도착하면 해당 출력이 끝난 뒤 수락하며, 명령이 먼저 수락되면 이전 표본을 버립니다. BLE 호출을 인터럽트 차단 구간 안에서 실행하지 않습니다. 스캔 콜백은 짧은 잠금으로 고정 크기 mailbox만 갱신하고, 모터 제어기·RSSI 이력·상태·Notify 주기는 `loop()`만 수정합니다. 빠르게 여러 명령을 받아도 최종 시작/중지 상태와 타깃을 보존합니다.
- 명령 로그는 `수신(처리 대기)`와 `요청 수락`을 구분합니다. 수락은 일반 뮤텍스 안에서 mailbox를 바꾼 시점이며, 모터 초기화는 이후 제어 주기에 적용합니다. 뮤텍스 생성이 실패하면 GPIO25를 0으로 둔 채 BLE 기능을 시작하지 않습니다.
- 1초 스캔은 완료 콜백을 사용하는 비동기 호출입니다. 진행 중 STOP/타깃 변경이 와도 모터는 다음 주기에 초기화되며, 기존 스캔은 완료 후 결과를 버립니다. 다음 스캔은 이전 결과의 읽기·해제가 모두 끝난 뒤 시작합니다.

## 로컬 검증

저장소 루트에서 `node scripts/test-cane-feedback.mjs`를 실행합니다. `CXX`/`CXX_ARGS` 또는 `.agent-loop/tools`의 격리 Zig 설치를 사용할 수 있습니다. 재접근, 누락 유예/감쇠, STOP/START, 타깃 초기화, 시각 역전/오버플로, 주기 독립성, 원시 RSSI Notify 및 명령/스캔 경합을 검증합니다.

ESP32 빌드는 `ble_stick.ino`와 `proximity-feedback.h`를 함께 스테이징한 뒤 Arduino CLI의 `esp32:esp32:esp32` 보드를 사용합니다. 현재 송수신 분리 경로는 Arduino-ESP32 3.3.12 / ESP-IDF 5.5.5의 Bluedroid로 컴파일 검증했습니다. NimBLE 경로는 빌드 단계에서 거절하며, 다른 코어 버전의 호환성·실제 MTU 협상·실물 PWM/BLE 동작은 검증하지 않았습니다.

## 테스트 상태
- 기존 펌웨어의 BLE 스캔, RSSI 측정, 진동 제어는 과거 실물 확인 기록이 있습니다. 이번 점진적 PWM·재접근·동시성 변경의 실물 확인 결과는 아닙니다.
- 상태 판정 기준값은 실환경 거리 테스트로 조정 예정 (현재 근접 테스트 기준)
- 새 펌웨어는 기기에 플래시하지 않았습니다. 왕복 거리·한 번/장기 누락·STOP·타깃 변경·연결 해제 후 재연결과 실제 모터의 약한 duty 구동을 재시험해야 합니다.
